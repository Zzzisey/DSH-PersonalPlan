# Personal Planner 新规划流程设计

> 状态：设计草案，记录截至 2026-11-09 已确认的业务语义与技术方向。
>
> 本文描述下一版规划流程，不代表当前代码已经实现。仍未确定的内容统一列在文末，避免把讨论中的方案误写成既定事实。
>
> 模块边界见 [`ARCHITECTURE_V2.md`](./ARCHITECTURE_V2.md)，实施和数据库演进见 [`MIGRATION_V2.md`](./MIGRATION_V2.md)。

## 1. 目标与原则

新流程要解决当前“一次性同时生成任务、时长和日期”的问题，把规划拆成三个有明确边界的内部阶段：

1. 先确定阶段与任务结构；
2. 再估算任务时长；
3. 最后安排日期并校验容量。

核心原则：

- 一个目标只承载一个可验收结果；
- 阶段就是里程碑，不再增加其他层级；
- 事件就是任务，任务是最小执行单位；
- 目标先正式创建，阶段和任务在用户确认前只存在于计划提案中；
- 三段内部流程完成后，用户只看一次最终日历预览；
- 预览确认前不修改正式阶段和任务；
- 系统提示词、工具描述、参数约束和校验器必须表达同一套规则；
- 确定性规则由代码保证，语义判断由当前 DeepSeek Harness Agent结合 System Prompt 与 Skill 完成；
- 多个对话可以各自生成提案，最终提交使用短事务锁，不能在等待 LLM 或用户时持锁。

## 2. 业务对象

业务层级固定为：

```text
Goal 目标
└── Phase 阶段/里程碑
    └── Task 任务/事件
```

`PlanProposal` 是唯一的规划工作流对象，不是第四个业务层级。本文中的“草稿”和“提案”指同一份 `PlanProposal`：草稿强调它尚未提交，提案强调它准备对正式计划产生的修改；二者不是两种类型、两张表或两套生命周期。

### 2.1 Goal：目标

目标先正式创建，再为它生成计划。

定义：

- 只表达一个可验收结果；
- 可以包含多个阶段；
- 没有计划的目标也可以存在；
- 目标完成以验收标准为准，不由“所有任务完成”自动推导。

建议字段：

| 字段 | 含义 |
|---|---|
| `title` | 单一结果的简短名称 |
| `acceptance_criteria` | 什么证据说明目标已经完成 |
| `motivation` | 为什么要做，可选 |
| `deadline` | 目标截止日期，可选 |
| `status` | `active / done / dropped` |

V2 对 `acceptance_criteria` 使用以下正式契约：

- staged 路径创建或更新 Goal 时必须提供；值在去除首尾空白后必须为 1–1000 个字符，内部换行和空白保留；
- v3 兼容迁移允许旧 Goal 暂时为 `null`，`null` 只表示“legacy 数据尚未补录”，不得写成空字符串；
- acceptance criteria 为 `null` 的旧 Goal 不能开始 staged Proposal，必须先由用户补录；
- `title / acceptance_criteria / deadline / status` 是会影响 Proposal 的规划字段；`motivation` 不是确定性校验或提交冲突字段。

状态含义：

- `active`：仍在追求这个结果；可以尚未规划、规划中或执行中；
- `done`：已经按目标验收标准确认结果达成；
- `dropped`：决定不再追求该目标，保留已有完成历史。

示例：

```text
目标：完成并发布求职作品集 V1
验收标准：公开链接可访问，包含 3 个完整项目案例
```

以下内容不是合格的单一目标：

```text
学习前端、制作作品集、准备面试
```

### 2.2 Phase：阶段/里程碑

阶段就是里程碑，没有独立的“里程碑”子层级。

定义：

- 一个阶段代表一个可验收的中间结果；
- 阶段下面只能有任务；
- 阶段不能嵌套阶段；
- 多个阶段通过 `seq` 表达规划和展示顺序；
- `seq` 是逻辑顺序，不自动等于强制的日期依赖。

建议字段：

| 字段 | 含义 |
|---|---|
| `title` | 里程碑名称 |
| `acceptance_criteria` | 做到什么算该里程碑完成 |
| `seq` | 在目标中的逻辑顺序 |
| `completed_at` | 空值表示未完成，有值表示已验收完成 |

V2 对 Phase 的 `acceptance_criteria` 采用与 Goal 相同的 1–1000 字符、去除首尾空白契约。新 Candidate Phase 必须具有非空验收标准；兼容迁移后的旧 Phase 可以暂时为 `null`，直到进入 staged 修改或重新规划时补齐。

阶段不再使用 `planned / active / dropped`。未完成且在重新规划后不再需要的阶段直接删除；已完成阶段保留。

示例：

```text
阶段：完成作品集内容初稿
验收标准：3 个项目案例均具备背景、行动、结果三个部分
```

### 2.3 Task：任务/事件

事件和任务是同一个概念。

定义：

- 任务是一次可以执行和完成的最小工作单位；
- 每个任务必须属于一个阶段；
- 任务没有子任务；
- 第一段只有标题和优先级；
- 第二段补充预计时长；
- 第三段补充日期；
- 不再支持不属于阶段的 `loose_tasks`。

正式任务建议字段：

| 字段 | 含义 |
|---|---|
| `title` | 要完成的动作或产物 |
| `priority` | `P0 / P1 / P2` |
| `est_minutes` | 预计时长 |
| `day` | 安排日期 |
| `seq` | 阶段内默认展示顺序 |
| `completed_at` | 空值表示未完成，有值表示已完成 |
| `actual_minutes` | 实际耗时，可选 |
| `note` | 执行笔记，可选 |

任务不再使用 `doing / dropped`：

- 当前没有计时或工作会话机制，无法可靠判断 `doing`；
- 未完成且不再需要的任务直接删除；
- 已完成任务始终保留。

## 3. 计划提案的业务含义

`PlanProposal` 的准确含义是：

> AI 准备怎样修改正式计划的一份待确认计划。它从三段规划开始时创建，在用户确认前始终属于草稿数据。

`PlanProposal` 是本文唯一的正式名称。“草稿”只是对其尚未提交性质的自然语言描述，不代表另一个对象。进入 `ready` 时也不会复制数据或创建新提案，只表示同一份 `PlanProposal` 已经完整，可以交给用户预览和确认。

提案可以表示：

- 新建计划：准备新增阶段和任务；
- 挪排期：准备改变已有任务日期；
- 局部修改：准备增删或修改部分阶段、任务；
- 重新规划：保留完成内容，删除不合理的未完成内容，并生成新计划。

`PlanProposal` 自身持久化一份规范化的完整候选计划，以便工具和 GUI 共享。Agent 每阶段只提交允许修改的字段，Host 校验后合并进这份 Candidate；Agent 的阶段输入不是另一份持久化快照。候选阶段和任务不是正式计划，不能参与正常任务查询和容量占用。

提案的下一步阶段与生命周期状态分开表达。`stage` 是唯一阶段事实源，表示下一次允许接受的阶段提交；Candidate 不再保存第二个 `contentStage`：

```text
stage: structure → estimate → schedule → ready

status: editing
          ↓
        awaiting_confirmation
          ├── 用户确认 → committed
          ├── 用户要求修改 → editing，并退回受影响阶段
          ├── 正式计划冲突 → stale
          └── 用户彻底放弃 → discarded
```

用户要求修改时，继续修改同一份 `PlanProposal`，退回最早受影响阶段并增加 revision。旧预览只在技术上失效，不需要作为业务版本展示给用户。

## 4. 新建计划的三段内部流程

三段流程由同一个 DeepSeek Harness Agent 在一个或多个 Step 中推进。场景入口负责建立提案上下文，共用提案工具负责保存、校验并推进阶段；插件内部不再直接调用裸 LLM 完成另一套规划循环。用户不需要逐段确认，只在全部阶段完成后看最终预览。

主流程如下：

```text
第一阶段：结构

DSH Agent 生成阶段、任务和优先级
  ↓
Agent 按 System Prompt + Skill 自检粒度与结构
  ↓
调用 planner_proposal_advance
  ↓
程序执行结构确定性校验
  ↓
通过，保存 Proposal 并进入估时阶段


第二阶段：估时

DSH Agent 按步骤和 15 分钟刻度补充任务时长
  ↓
Agent 按 System Prompt + Skill 自检估时与任务粒度
  ↓
调用 planner_proposal_advance
  ↓
程序执行时长确定性校验
  ↓
通过，保存 Proposal 并进入排期阶段


第三阶段：排期

DSH Agent 补充任务日期
  ↓
Agent 按 System Prompt + Skill 评审排期语义
  ↓
调用 planner_proposal_advance
  ↓
程序执行日期、容量和顺序校验
  ↓
通过，保存 Proposal 并进入 ready


最终结果

服务器计算 baseline 与 candidate 的 Diff
  ↓
日历展示最终提案预览
  ↓
用户确认
  ↓
写入正式阶段和任务
```

### 4.1 第一段：结构与粒度

本段只生成：

- 阶段标题；
- 阶段验收标准；
- 阶段顺序；
- 任务标题；
- 任务优先级。

禁止出现：

- 任务时长；
- 任务日期；
- 阶段起止日期；
- 过度详细的操作说明。

检查范围：

- 目标是否只表达一个结果；
- 目标是否可验收；
- 阶段是否是可验收里程碑；
- 阶段数量是否越界；
- 是否存在空阶段；
- 任务是否太粗、太细或重复；
- 任务是否明确属于某个阶段；
- 阶段和任务是否覆盖目标。

### 4.2 第二段：估算时长

本段只给第一段已有任务补充估时，不得偷偷改变结构或日期。

估时方法：

1. 先判断完成任务包含多少个实际步骤；
2. 再按 15 分钟刻度估算总时长；
3. 每条任务的预计时长应落在 15–120 分钟。

确定性检查：

- 每个任务都有估时；
- 时长是 15 分钟的整数倍；
- 时长在 15–120 分钟；
- 不允许缺失时长后默认补 30 分钟。

语义检查：

- 步骤数量与总时长是否明显不匹配；
- 是否存在大量无意义的 15 分钟碎片；
- 是否把同一个任务机械拆成多个操作步骤；
- 估时是否与业务场景明显不符。

修复规则：

- 仅时长值不合法：留在第二段修复；
- 任务边界本身不合理：退回第一段合并、拆分或重写任务，已有估时失效。

### 4.3 依赖分析

依赖分析发生在任务结构和估时稳定之后、正式排期之前。

流程：

```text
任务结构和时长已确定
  ↓
当前 DSH Agent 只判断任务先后关系，不看候选日期
  ↓
输出结构化 ordering constraints
  ↓
当前 DSH Agent 在这些约束下生成日期
  ↓
代码确定性检查日期是否违反约束
```

内部结构至少包含：

- 前置任务；
- 后置任务；
- `required / preferred`；
- 原因。

结构化输出用于代码定位任务、检测循环、比较日期和自动化测试。第一版不把依赖做成 Task 的正式业务字段，而是保存在提案校验元数据中。

已知边界：

- 代码能保证 LLM 已识别出的硬依赖不被违反；
- 系统不能保证 LLM 一定发现所有隐含依赖；
- 结构发生变化时重新分析依赖；
- 只调整日期时可以复用并重新检查已识别的依赖。

### 4.4 第三段：排期与最终校验

本段只给已有任务补充日期。

排期时需要同时考虑：

- 当前目标的任务；
- 其他目标已经占用的每日容量；
- 工作日、周末和单日覆盖容量；
- 目标截止日期；
- 任务优先级；
- 已识别的任务依赖；
- 业务语义上的合理顺序和缓冲。

每日负载口径：

```text
最终日负载
= 所有目标在该日已有的未完成任务
+ 当前提案准备排入该日的任务
- 当前提案准备删除或移出该日的任务
```

已经完成的任务不占未来剩余容量。

## 5. 最终校验与用户动作

已确认不再使用 `warn`。轻微建议由对话智能体作为附加说明表达，不进入正式 verdict。

第一版不允许用户 override 超容量或超过截止日期。两者都是阻止 Proposal 进入 `ready` 的确定性错误，Agent 必须修改排期后重新提交；因此第一版正式 validation verdict 只有 `valid / invalid`，不定义 `requires_override` 或 `needs_decision`。硬性错误同样始终不能确认提交。

用户面对最终预览始终只有两个核心动作：

- 确认：提交；
- 取消并修改：不提交，继续让 AI 修改提案。

LLM 超时、输出无法解析、数据库繁忙和并发冲突属于工具运行状态，不属于计划 verdict。

## 6. 场景化操作

### 6.1 新建计划

适用场景：正式目标已经创建，但还没有正式阶段和任务。

内部执行完整流程：

```text
结构 → 估时 → 依赖分析 → 排期 → 最终预览
```

确认后，在现有目标下原子创建正式阶段和任务。

### 6.2 挪排期

适用场景：计划内容和估时没有问题，只是因为进度变化需要调整日期。

只允许修改：

- `day`。

不允许修改：

- 阶段；
- 标题；
- 优先级；
- 预计时长；
- 任务边界。

只需要重跑依赖、日期和容量相关校验。

### 6.3 局部修改

适用场景：已有计划局部不合理，需要改少量阶段、任务或估时。

校验起点由最早受影响的步骤决定：

| 修改内容 | 重新校验起点 |
|---|---|
| 只改日期 | 第三段，实际应归入挪排期 |
| 改预计时长 | 第二段，然后重跑依赖和排期 |
| 改标题、优先级、增删任务 | 第一段 |
| 增删或修改阶段 | 第一段 |

### 6.4 重新规划

适用场景：原计划整体思路已经不合理，需要替换大部分未完成计划。

规则：

- 已完成阶段保留；
- 已完成任务保留；
- 未完成但新计划仍然需要的阶段可以保留并替换其未完成任务；
- 不再需要的未完成阶段直接删除；
- 不再合理的未完成任务直接删除；
- 新的未完成计划重新走完整三段流程。

第一版不维护被删除的未完成任务的业务状态，也不提供正式计划历史恢复。

## 7. 工具边界

按照业务逻辑内聚原则，场景入口负责表达用户意图，四种场景共用同一套 Proposal Engine；阶段推进由一个共用工具完成，不能分别实现四套规划逻辑。

| 工具 | 职责 |
|---|---|
| `planner_plan_create` | 为已有目标开始一份新计划提案，从结构阶段进入 |
| `planner_plan_reschedule` | 开始只调整已有任务日期的提案，从排期阶段进入 |
| `planner_plan_modify` | 开始局部修改，并由最早受影响字段决定重跑阶段 |
| `planner_plan_replan` | 开始整体替换未完成计划，保留已完成内容 |
| `planner_proposal_advance` | 提交当前阶段产物，保存、校验并推进或退回 |
| `planner_proposal_get` | 恢复当前提案和下一步所需的有限上下文 |
| `planner_proposal_commit` | 用户明确确认后提交 ready 提案 |
| `planner_proposal_discard` | 明确放弃提案 |

这些工具共用同一套提案、校验和提交引擎。是否最终保留四个场景入口，还是通过 Tool Eval 收敛为一个带 `operation` 的入口，仍需评估；但 PlannerService 中四种业务语义必须保持分离。

工具描述固定说明：

1. 什么时候使用；
2. 不该什么时候使用；
3. 参数约束；
4. 返回字段语义；
5. 可恢复错误的下一步操作。

工具返回给对话智能体的数据应保持小而可编排，只包含：

- 执行状态；
- 目标语义名称和内部引用；
- 提案引用；
- 操作类型；
- 校验结果；
- 简要变更统计；
- 是否需要用户接受风险；
- 下一步动作；
- GUI 是否已有可预览提案。

工具不应把整份计划返回给对话智能体暴力扫描。完整预览由 GUI 按需读取。具体 JSON schema 尚未确定。

## 8. 日历 GUI 预览

三段流程全部完成后，日历进入“提案预览模式”。正式数据此时没有变化。

### 8.1 颜色规则

| 变化 | 日历表现 |
|---|---|
| 新增任务 | 护眼绿色 |
| 删除任务 | 红色 |
| 移动任务 | 原日期红色删除，新日期绿色新增 |
| 同日期修改属性 | 旧版本红色，新版本绿色 |
| 未变化任务 | 默认样式 |

新建计划没有旧基线，所有任务都可以使用护眼绿色，不需要避免“大面积绿色”。

修改时长后，日期容量条只显示提案提交后的新值，不同时展示旧容量。

移动任务在 GUI 接口中按“删除 + 新增”展示：

```text
11 月 10 日
- [红色] 撰写项目案例 · 30 分钟

11 月 12 日
+ [绿色] 撰写完整项目案例 · 60 分钟
```

服务端内部仍通过任务 ID 判断它是不是同一条正式任务，以正确更新而不是错误地创建重复任务。

### 8.2 页面行为

预览顶部显示：

```text
正在预览计划提案 · 尚未保存
新增 N 项 · 删除 N 项 · 调整 N 项
```

提供：

- `确认计划`；
- `取消并继续修改`；
- `彻底放弃提案`（可以放到次级操作）。

确认后：

1. 原子提交正式阶段和任务；
2. 日历退出预览模式；
3. 绿色任务恢复默认样式；
4. 红色任务消失；
5. 月历、每日清单和今日负载统一刷新。

取消并修改后：

1. 正式计划保持不变；
2. 当前预览失效；
3. AI 更新同一份提案；
4. 日历只展示最新预览。

跨月移动必须在两个视图中保持同一结果：原月份显示红色删除，目标月份显示绿色新增。

### 8.3 预览数据来源

`plan_proposal` 保存 `baseline` 和当前完整 `candidate`；日历接口由服务器比较二者计算 diff，并按当前月份返回 GUI 所需数据。Diff 是预览结果，不是另一份提案，也不参与三段规划。

这样可以：

- 统一新增、删除和修改的判断；
- 避免每个客户端重复实现 diff；
- 只加载当前可见月份；
- 不把大计划塞进对话智能体上下文。

具体预览接口结构尚未确定。

## 9. 多对话并发

每个对话可以拥有自己的独立 `PlanProposal`。三段生成和用户预览期间不锁正式日历。

每份提案至少记录：

- 它生成时看到的正式计划快照；
- 当时的 `schedule_version`；
- 当前提案快照；
- 所属对话。

容量与正式计划共用全局 `schedule_version`。容量规则、正式 Phase/Task，或 Goal 的 `title / acceptance_criteria / deadline / status` 成功变化时版本只增加一次；只改 `motivation` 不增加。版本变化是提交时必须重新读取和比较的信号，不代表所有 Proposal 一律冲突：只有目标基线、Candidate 涉及日期的容量/外部占用或其他确定性约束实际变化时才使旧预览 `stale`。容量变化不得在沿用旧预览的情况下静默提交。

### 9.1 正常提交

```text
用户确认
  ↓
BEGIN IMMEDIATE，获取短写锁
  ↓
重新检查 Proposal 所属 Session、revision、状态和正式版本
  ↓
读取最新正式计划和 schedule_version
  ↓
检查提案是否仍可安全应用
  ↓
重算容量和确定性约束
  ↓
写入正式数据，schedule_version + 1
  ↓
COMMIT，释放锁
```

不能在事务锁内等待 Agent、模型或用户输入。

### 9.2 两份提案互不影响

例如一份只改 11 月 10 日，另一份只改 11 月 20 日，且没有共享任务或容量影响，可以在重新校验后分别提交。

### 9.3 同一任务被修改

例如：

```text
对话 A：把任务 X 从 10 日移到 11 日
对话 B：把任务 X 从 10 日移到 12 日
```

A 先提交后，B 的旧预览不能直接覆盖最新状态。

处理方式：

1. 旧预览失效；
2. 保留 B 的意图“最终希望 X 在 12 日”；
3. 基于最新状态生成新预览“X 从 11 日移到 12 日”；
4. 用户再次确认。

如果任务已经完成或删除，无法安全自动套用原意，应返回冲突并请求用户处理。

### 9.4 不同任务造成容量冲突

例如 A、B 都向同一天增加任务。A 提交后，B 再提交时必须按照最新日历重算容量：

- 仍然合法：可以继续提交；
- 需要改变 B 的日期或内容：生成新预览并重新确认；
- 硬性不合法：拒绝提交。

## 10. 数据设计方向

第一版不引入正式的 `plan_revision` 业务对象。为兼容现有数据，新增 `plan_proposal` 表而不原地破坏旧 `draft`。`plan_proposal` 是 V2 唯一的候选计划表；旧 `draft` 只承载 legacy 流程，二者不是草稿与提案的前后两份数据。最小数据集合为：

```text
正式业务数据：goal / phase / task
待确认提案：plan_proposal
旧流程兼容：draft（迁移期只保留，不承载新提案）
并发计数：schedule_version
当前校验结果：plan_proposal.validation_json
旧流程日志：check_log
```

需要调整的现有数据：

- `goal` 增加验收标准；
- `phase` 增加验收标准和完成时间，继续使用 `seq`；
- `task` 增加阶段内顺序和完成时间，移除对 `doing/dropped` 的依赖；
- 新增 `plan_proposal`，保存操作类型、阶段、状态、所属对话、基线快照、当前候选快照、revision、基线 `schedule_version` 和校验结果；
- 旧 `draft / check_log` 在兼容期保留，不自动转换成 V2 `PlanProposal`；
- `setting` 或独立元数据位置保存全局 `schedule_version`。

v3 采用 `planner_meta.schedule_version`，不另设 `capacity_version`。Proposal 的 schedule validation 会持久化 Candidate 涉及日期的容量检查输入与结果，使 commit 能区分无关版本变化和会改变预览的容量变化。

正式 `task.est_minutes` 可以继续保持非空，因为只有三段流程全部完成后才创建正式任务。第一段中缺失的时长和日期只存在于 `PlanProposal.candidate` 中。

旧数据迁移至少需要处理：

- 旧目标和阶段没有验收标准；
- 旧任务状态含有 `doing/dropped`；
- 旧 `draft` 记录不符合三段 `PlanProposal` 格式；
- 当前正式任务需要成为新的初始基线。

## 11. 系统提示词、工具和 Skill

### 11.1 系统提示词

系统提示词应始终包含：

- Goal、Phase、Task 的核心定义；
- 三段流程及每段允许/禁止的字段；
- 三段完成前不能声称正式任务已创建；
- 用户只在最终日历预览后确认；
- 没有用户明确确认不得 commit；
- 少量稳定的正反例。

### 11.2 工具与校验器

工具 schema 和代码校验负责不可绕过的边界，例如：

- 第一段出现时长或日期时拒绝；
- 第二段出现日期时拒绝；
- 时长不是 15 分钟刻度时拒绝；
- 提案未准备好时禁止 commit；
- 并发冲突时禁止覆盖正式数据。

### 11.3 业务 Skill

Skill 用于补充特定业务场景知识，而不是重复通用流程，例如：

- 运营排期的典型任务粒度、审核链路和缓冲；
- 求职准备中简历、岗位研究、面试复盘的典型粒度；
- 科研阅读、实验、写作的常见拆分和估时；
- 软件开发中编码、测试、部署和评审的依赖。

Skill 直接进入当前 DSH Agent 的上下文，不需要再传给工具内部的规划 LLM。提案可以记录使用过的 Skill 名称或版本作为诊断元数据，但它不参与正式业务对象层级。

## 12. 暂不纳入第一版

- 正式任务硬依赖关系；
- 小时级时间表；
- `doing` 状态和计时机制；
- 被删除的未完成任务历史；
- 正式计划版本浏览和一键回滚；
- 中间三段逐段让用户确认；
- 日历中的部分接受/部分拒绝；
- 多用户实时协作。

## 13. 尚待确定

以下内容需要继续讨论后才能进入实现：

1. 阶段数量上下限、每阶段任务数量等结构阈值；
2. 同一天的硬依赖是允许并附加说明，还是必须拆到不同日期；
3. 场景化工具的精确参数和结构化返回 schema；
4. 日历月份预览 API 的精确数据结构；
5. 提案过期时间和页面刷新后的恢复行为；
6. DSH Agent 的三段提示词、工具重试上限、失败降级和 Eval 标准；
7. 业务 Skill 的选择、版本记录和注入机制；
8. 旧数据迁移时 `doing/dropped` 在最终移除 legacy 状态列时的具体物理转换方式；
9. 重新规划时“保留未完成阶段并替换任务”的准确匹配规则。
